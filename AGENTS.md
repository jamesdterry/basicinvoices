# Basic Invoices

```
App name:           Basic Invoices (basicinvoices)
Super-admin env:    SUPER_ADMIN_EMAIL=<consultant's email>
Public origin:      BASE_URL=https://basicinvoices.fly.dev
Roles (high → low): super_admin → subcontractor
Cookie prefix:      bi_   (bi_session, bi_csrf)
Departures:
  - Two roles only; no per-project role tiers.
  - Subs never see rates or invoices; their UI is "log my hours".
  - Super-admin can also be a project_member at a per-project rate (self-bill).
  - Public unauthenticated invoice view at /i/<token> (HTML + PDF).
  - Recurring tick triggered by wake-on-activity (/api/me) + a daily GitHub Action TOTP-pinging /cron/recurring-tick. Fly runs with auto_stop_machines = "stop" + min_machines_running = 0.
  - USD only in v1; no currency column anywhere.
  - No public API; /api/* routes are internal SPA endpoints only.
```

Open-source invoicing aimed at solo consultants. Vanilla JS/CSS/HTML on a Node + Express server backed by SQLite (`better-sqlite3`). Deploys to fly.io.

## Working with this codebase

- **Only commit when explicitly told to.** `git add` and `git commit` are fine on a direct request from the maintainer for that single commit; do not generalize an approval to subsequent work. Read-only git commands (`status`, `diff`, `log`, `show`, `blame`) are always fine.
- **Never push to a remote.** No `git push` (including `--force`), no `git push --tags`, and no tool action that triggers a push (e.g. `gh pr create` from a not-yet-pushed branch). The maintainer pushes manually.

## Stack & conventions

- **Server:** Node LTS, Express, `better-sqlite3`, bcrypt, nodemailer, helmet, `puppeteer-core` + `@sparticuz/chromium` (PDF rendering, Stage 6), `stripe` (optional, Stage 7A — gated on `STRIPE_SECRET_KEY`; lazy client construction so `vi.mock('stripe', ...)` works in tests).
- **Client:** hand-rolled vanilla ESM modules (`<script type="module">`), single `app.css`. **No build step.**
- **Layout:** `server/{routes,services,db,middleware,timers,views}`, `public/{lib,components,views}/`, `test/`, `e2e/`, `scripts/`.
- **Frontend modules:** `public/lib/state.js` (event emitter + `h()` DOM helper), `public/lib/router.js` (hash router; add routes to its `ROUTES` table, not ad-hoc; query string is parsed into `params.query`), `public/lib/api.js` (`getJson`/`postJson`/`patchJson`/`putJson`/`deleteJson`/`qs` — 401 auto-redirects to `/login.html`; CSRF double-submit reads `bi_csrf` and sends `X-CSRF-Token`), `public/lib/debounce.js`, `public/lib/filters.js` (list-view filter state — URL/`localStorage` round-trip; used by the time-entries view, future stages will reuse for invoices/payments/reports), `public/lib/money.js` (`formatMoney(cents) → '$1,234.56'`, USD only). Future stages will add `public/lib/relativeTime.js`. Components are DOM-returning functions in `public/components/`; route views go in `public/views/`.
- **`localStorage`:** namespace user-scoped keys as `basicinvoices.<feature>.${userId}.${scopeId}` (see `filters.js`).
- **CSP:** helmet defaults block inline scripts/styles. No inline event handlers (`onclick=`), no inline `style=`, no `eval`/`new Function`. Bind events with `addEventListener` (or the `on*` keys in `h()`).
- **App shell auth:** `/` and `/index.html` are gated by `loadSessionFromCookie` (exported from `middleware/requireUser.js`); other static assets are public. `/i/<token>` (public invoice view) is also public and **does not consult the session cookie**.
- **Migrations:** append-only `server/db/migrations/*.sql`; never edit a shipped migration.
- **Transactions:** any multi-table write runs inside `db.transaction(...)`.
- **Permissions:** access gates live in middleware (`requireUser`, `requireSuperAdmin`, `requireProjectMember`) and are applied at the route layer. Services own role-aware *filtering* — `services/projects.js#listForUser` narrows by membership, `services/projectMembers.js#stripRates` removes `bill_rate_cents` from non-super-admin payloads (reusable for any future payload that joins in a rate), and `services/timeEntries.js#list` forces sub callers to their own rows + memberships. Expenses + milestones are super-admin only — `services/expenses.js` and `services/milestones.js` short-circuit non-super-admin actors to `'forbidden'`, and the `requireSuperAdmin` middleware on `/api/expenses` and `/api/milestones` blocks subs at the route layer too.
- **Locking on invoice:** time entries, expenses, and milestones all become read-only once `invoice_id` is set. Mutating a locked row returns 409 `'locked'`. Stage 5 invoice creation snapshots `unit_rate_cents` from `project_members` and writes `invoice_id` on the source rows; `void`/`deleteDraft` clear it. (`invoice_id` columns are declared without an FK until Stage 5's `0006_invoices.sql` table-rebuilds them — SQLite refuses INSERTs on a child whose declared parent is missing, even when the FK column is NULL.)
- **History:** services write to `admin_audit` + `audit_changes` via `services/audit.js#logAction`. Resolve FK ids to display strings (e.g. "Acme — Website") before calling — the audit row is the human-readable record.
- **PDF + email (Stage 6):** `services/invoicePdf.js` lazy-launches one `puppeteer-core` + `@sparticuz/chromium` browser per process and reuses it; LRU keyed on `${invoice.id}:${invoice.updated_at}` (cap 32); closed in the SIGTERM handler. `services/invoiceMail.js` orchestrates `getByPublicToken` → `renderInvoiceHtml` → PDF buffer → `services/email.js#sendEmail` with the PDF as an attachment + the public `/i/<token>` link in the body. `services/email.js#sendEmail` accepts `attachments: [{ filename, content, contentType }]`; the dev-mode `dev-email` log records attachment metadata (filename + bytes) but not the bytes themselves. `invoices.send()` blocks with reason `'no_client_email'` (HTTP 409) when `clients.contact_email` is null. `POST /api/invoices/:id/resend-email` writes `'invoice.resend_email'` audit and re-dispatches without mutating invoice state. `GET /i/<token>.pdf` serves the cached PDF inline (`Content-Disposition: inline; filename="Invoice-YYYY-NNNN.pdf"`); same rate-limit + revoke + cache headers as the HTML route. The browser is skipped under `config.isTest` unless `BI_PDF_ENABLED=1` (the e2e suite sets it; vitest does not — the public PDF route returns 503 `pdf_unavailable` in vitest). Chromium binary resolution: `PUPPETEER_EXECUTABLE_PATH` env override → installed Chrome on darwin (Google Chrome / Chromium / Edge under `/Applications`) → `@sparticuz/chromium#executablePath()` for Linux/Docker. The darwin shortcut keeps `npm run e2e` working out of the box on a developer Mac because `@sparticuz/chromium` ships a Linux-only binary.
- **Payments (Stage 7):** `services/payments.js` records receipts against invoices with `status IN ('sent','paid')` (drafts/voids reject `'wrong_status'`). Every `create`/`update`/`remove` runs in a transaction that calls a private `recomputeInvoiceTotals(invoiceId)` to refresh `invoices.amount_paid_cents` and flip status `sent → paid` once `amount_paid >= total_cents`. **No auto-revert from `paid`** — if a payment is later edited or deleted such that `amount_paid < total`, status stays `paid` and the operator decides whether to void. Payments aren't lockable; the parent invoice's status is the gate. `payments.invoiceHasPayments(db, invoiceId)` is the companion guard consumed by `services/invoices.js`: `voidInvoice` and `deleteDraft` both reject with `'has_payments'` (HTTP 409) when payments exist — the `payments.invoice_id` FK is `ON DELETE RESTRICT`, so the operator must delete payments before voiding/deleting. Routes: `GET /api/invoices/:id/payments`, `POST /api/invoices/:id/payments` (returns `{ payment, invoice }` so the UI sees the post-recompute status without a refetch), `PATCH /api/payments/:id`, `DELETE /api/payments/:id`. The Stripe Payment Link URL is editable post-send via `invoices.setStripeLink` (allowed on `draft` + `sent`; `PUT /api/invoices/:id/stripe-link`); `updateDraft` keeps its own draft-only Stripe handling.
- **Recurring (Stage 8):** `services/recurring.js` schedules per-project monthly drafts from `recurring_schedules`. Modes `time_and_expenses` (sweeps unbilled time + expenses through today via `invoices.createDraft`) and `fixed_milestone` (inserts a `milestones` row first, then drafts so the milestone is pulled into a single line). `runDue(db, { now })` resolves `SUPER_ADMIN_EMAIL` → real user once per tick and uses that as `actor` for `invoices.createDraft` / `milestones.create` / `stripeLinks.generate` / `invoices.send` so audit + `created_by` columns attribute correctly. (Departure from the spec's `id: null` synthetic actor: `milestones.created_by` is NOT NULL with an inner JOIN on `users`, so a real id avoids a schema rebuild.) Each schedule's run is wrapped in its own try/catch + transaction — one failure doesn't block siblings; failures land in `error_log` + audit `'recurring.run'` with `meta.status='error'` and `next_run_date` is NOT advanced (operator fixes, retry on next tick). `time_and_expenses` with no accrued lines audits `meta.status='skipped'` and DOES advance `next_run_date`. `auto_stripe_link=1` triggers `stripeLinks.generate` *outside* the transaction after the draft commits; failures are caught (already logged to `error_log` by stripeLinks itself) and audit flips to `meta.status='partial'` but the draft still drops. `auto_send=1` (Stage 8.6) calls `invoices.send` + `invoiceMail.sendInvoiceEmail` *after* the Stripe-link block (so the email body sees the Payment Link URL); send failures (`no_client_email`, SMTP throw, etc.) are caught, logged to `error_log`, and surface as audit `meta.send=<reason>` + `meta.status='partial'` — the draft persists for manual recovery. `invoices.send` failures BEFORE the email dispatch leave the invoice in `draft`; SMTP failures AFTER `invoices.send` flipped status to `sent` do not roll back (matching the route-level `POST /api/invoices/:id/send` behavior — operator uses `resend-email`). `day_of_month` is constrained to 1..28 (schema CHECK); `advanceNextRunDate` adds one calendar month, `computeFirstRunDate` jumps to the next occurrence ≥ today. `resume()` bumps `next_run_date` forward when it has drifted into the past so a long pause doesn't backfire on the next tick. Routes: `GET/PUT/DELETE /api/projects/:id/recurring`, `POST .../{pause,resume,run-now}`, `GET /api/admin/recurring` (list), `POST /api/admin/recurring/run-now` (batch). The `runOnce` route honors `paused_at` (rejects `'paused'`/409) but ignores `next_run_date` so the operator can force-run a future-dated schedule.
- **Recurring trigger paths (Stage 8.5):** with `auto_stop_machines = "stop"` + `min_machines_running = 0`, the in-process `setInterval` timer can't be relied on. Three convergent triggers all flow through `recurring.maybeRunDue`: (1) the legacy in-process timer in `server/timers/recurringTick.js` — only useful while the machine is up for other reasons; (2) **wake-on-activity** in `routes/me.js` — fires `setImmediate(() => maybeRunDue(db))` after the response so the consultant's app-shell load drives the tick; (3) **TOTP-gated cron** at `POST /cron/recurring-tick` (mounted before `csrf` in `server/index.js`, parallel to `/i/`) — called daily by `.github/workflows/recurring-tick.yml`, which uses `scripts/totp-code.js` to compute a 6-digit code from `RECURRING_TICK_SECRET` and POSTs `X-Recurring-Tick: <code>`. The HTTP request itself wakes a stopped fly machine via `auto_start_machines = true`. `services/recurring.js#tryClaimTick` is the atomic claim — `UPDATE _recurring_meta SET last_tick_at = ? WHERE id = 1 AND last_tick_at < cutoff` — so concurrent triggers can't double-run; only the first writer in a 1-hour window matches. When the claim is already held by a recent trigger (e.g. wake-on-activity ran in the last hour), the cron route returns `200 { results: [], skipped: true }` so the GH Action doesn't alarm — schedules become due at midnight UTC and stay due all day, so a "skip because someone else just ran" is always safe. TOTP is RFC 6238, HMAC-SHA1, ±1 step (±30s) skew, in `server/lib/totp.js`. Without `RECURRING_TICK_SECRET` set, the cron route returns 503 `'tick_disabled'` and only paths (1)+(2) are available — fine for local dev. The cron route is rate-limited (6 req/min/IP) to blunt brute-force against a 6-digit code.
- **Stripe Payment Links (Stage 7A):** `services/stripeLinks.js` wraps Stripe's Payment Links API behind an optional service gated on `STRIPE_SECRET_KEY` (`config.stripeSecretKey`); the Stripe client is constructed lazily so `vi.mock('stripe', ...)` in tests intercepts the constructor. `isEnabled()` returns true iff a key is set; both the new route and `/api/me` consume it. `generate(db, invoiceId, { actor, ip, force = false })` — super-admin only; allowed on `draft` + `sent` (else `'wrong_status'`); idempotent when `stripe_payment_link_id` is non-null unless `{ force: true }` is sent; calls `stripe.paymentLinks.create({ line_items: [...], metadata: { invoice_id, invoice_number } })` with `currency: 'usd'` + `unit_amount: total_cents`; persists `stripe_payment_link_url` + `stripe_payment_link_id` and audits `'invoice.generate_stripe_link'` with a `changes` array. Stripe SDK errors **never throw out** — they're caught, written directly to the `error_log` table (no helper service; `db.prepare('INSERT INTO error_log ...').run(...)`), logged via pino, and surface as `'stripe_failure'` (HTTP 502). Without a key the route returns 503 `'stripe_disabled'`. `deactivate(db, invoiceId)` is best-effort (called fire-and-forget from `voidInvoice` after the void transaction commits — failures are logged but never roll the void back). `setStripeLink` clears `stripe_payment_link_id` to NULL on each save so a stale id can't outlive the URL it pointed to. Route: `POST /api/invoices/:id/stripe-link/generate` (body `{ force?: boolean }`). `/api/me` exposes `stripe_enabled: boolean` so the SPA shows/hides the Generate / Regenerate button without round-tripping. Manual paste (Stage 7) keeps working when no key is set.
- **Money:** stored as integer cents everywhere; rates are `INTEGER`-cents-per-hour; hours are `REAL`. USD only in v1, no currency column.
- **Tests:** vitest + supertest in `test/` (fresh in-memory DB via `test/db.js`); Playwright + chromium in `e2e/` (file-backed `./data/e2e.sqlite` seeded by `scripts/seed-e2e.js`, server on `:8081` via `npm run start:e2e`, authed specs reuse `.auth/super_admin.json` and `.auth/subcontractor.json` storage state). Run e2e with `npm run e2e` (one-time `npm run e2e:install` for the browser).

## Roles

Super admin (env `SUPER_ADMIN_EMAIL`) → subcontractor.

Subs only see projects where they are a member; super-admin sees all. Subs never see rates or invoices anywhere in the UI — the service layer strips `bill_rate_cents` from non-super-admin payloads. Project-membership enforcement lives in `middleware/requireProjectMember.js`.

**User provisioning:** the magic-link flow auto-bootstraps the super-admin email on first login; there is no admin UI for creating subcontractors yet. To add a sub for local dev, insert directly: `sqlite3 data/basicinvoices.sqlite "INSERT INTO users (email, display_name, role, created_at, updated_at) VALUES ('sub@example.com', 'Sub', 'subcontractor', datetime('now'), datetime('now'));"`. The e2e suite's sub user is seeded by `scripts/seed-e2e.js`.

## Domain glossary

- **Client** — a billable entity (one company / person you invoice). Owns many projects. Never logs in.
- **Project** — work performed for a client. Owns time entries, expenses, milestones, and one optional recurring schedule.
- **Project member** — a user (super-admin or subcontractor) attached to a project at a specific bill rate.
- **Time entry** — a sub or super-admin's logged hours on a date for a project. Locked once attached to an invoice.
- **Expense** — super-admin–entered out-of-pocket cost on a project. Locked once invoiced.
- **Milestone** — super-admin–entered fixed-amount line item on a project (retainers, deliverables). Locked once invoiced.
- **Invoice** — bills a client for one project's accumulated/fixed lines. Statuses: `draft` → `sent` → `paid`, plus `void`. Has a public `/i/<token>` view (HTML + PDF).
- **Invoice line** — a row on an invoice, sourced from time/expense/milestone with rates **snapshotted** at creation.
- **Payment** — recorded receipt against an invoice (date, amount, method, reference). Service flips status to `paid` when fully covered.
- **Recurring schedule** — per-project monthly cadence that drops a draft invoice (time-and-expenses or fixed-milestone) for super-admin review. Drafts can be auto-sent on each tick when the schedule's `auto_send` flag is set (Stage 8.6); without it, drafts wait for manual review.
